项目13学习路径
——分布式计算任务安全分发与结果审计平台

说明
============================================================

这个项目是严格的 C/S 架构：

服务端：Python，负责监听连接、认证节点、拆分和分配任务、验证结果、
        多数表决、信誉管理、审计记录和可视化控制。

客户端：Windows C，负责连接服务端、身份认证、验证任务签名、执行计算、
        生成 Merkle 证明、提交结果并持续发送心跳。

建议不要一开始从 gui.py 往下硬读。应当按照“网络基础 → 协议 → 安全 →
业务 → 界面 → 完整流程”的顺序学习。


第一阶段：先理解整个 C/S 架构
============================================================

一、要学什么

1. 什么是服务端和客户端。
2. 服务端为什么要先启动并监听端口。
3. 客户端为什么主动连接服务端。
4. 一条连接建立后，双方如何轮流发送消息。
5. 网络层、业务层、安全层为什么要分开。

二、本项目总体流程

1. 启动服务端，监听 127.0.0.1:8888。
2. 手动启动客户端。
3. 客户端连接服务端。
4. 客户端提交身份、许可证和程序哈希。
5. 服务端认证客户端并建立加密会话。
6. 客户端发送心跳，表明自己在线。
7. 服务端向客户端发送经过签名的计算任务。
8. 客户端验签，执行计算并生成 Merkle 证明。
9. 客户端把结果和证明发回服务端。
10. 服务端验证证明并收集多个节点的结果。
11. 服务端进行多数表决，得到可信子任务结果。
12. 服务端合并所有子任务，得到最终结果。
13. 服务端更新信誉、保存审计记录并在 UI 显示状态。
14. 客户端不退出，继续发送心跳并等待下一项任务。

三、先看哪些文件

服务端入口：server/server.py
客户端控制台入口：client/client.c
客户端业务主流程：client/client_logic.c
服务端业务主流程：server/task_service.py

四、学完后的过关问题

能够不用看代码，说清楚“客户端连接到最终结果产生”的完整顺序。


第二阶段：TCP 套接字基础
============================================================

模块一：Windows C 客户端套接字

一、要学什么

1. IP 地址表示一台主机，端口表示主机上的一个网络服务。
2. TCP 是面向连接、可靠、有序的字节流协议。
3. SOCKET 是 Windows 对网络连接的表示。
4. 客户端连接失败、超时和服务端关闭时应该怎样处理。

二、客户端套接字流程

1. WSAStartup
   初始化 Windows 的 Winsock 网络库。

2. socket
   创建一个 TCP 套接字。
   本项目使用 AF_INET 和 SOCK_STREAM。

3. 设置 sockaddr_in
   填写服务器 IP、端口和地址族。

4. connect
   主动连接服务器。

5. send
   向服务器发送数据。

6. recv
   从服务器接收数据。

7. shutdown 或 closesocket
   断开连接并释放套接字。

8. WSACleanup
   释放 Winsock 环境。

三、本项目对应文件

client/network.c
client/network.h

重点函数：网络初始化、带超时连接、有限重连、完整发送、完整接收、关闭连接。

四、过关标准

能够独立写出一个连接 127.0.0.1:8888、发送字符串并接收回复的客户端。


模块二：Python 服务端套接字

一、服务端套接字流程

1. socket.socket
   创建 TCP 套接字。

2. setsockopt
   设置地址复用等套接字选项。

3. bind
   把服务端绑定到指定 IP 和端口。

4. listen
   进入监听状态，建立等待连接队列。

5. select
   等待监听套接字变为可读，避免一直空转。

6. accept
   接收一个客户端连接，获得新的客户端套接字。

7. 把客户端连接交给线程池处理。

8. 客户端结束后关闭对应套接字。

二、本项目对应文件

server/server.py

三、必须理解

监听套接字只负责接收新连接；accept 返回的新套接字才负责和某个客户端通信。

四、过关标准

能够解释 bind、listen、accept 的区别，以及服务端为什么不能只用一个套接字
同时完成监听和所有客户端通信。


第三阶段：TCP 粘包、拆包与私有协议
============================================================

模块三：TCP 是字节流

一、要学什么

TCP 不保留消息边界。一次 send 不一定对应一次 recv：

1. 一条消息可能被拆成多次接收，这叫拆包。
2. 多条消息可能一次接收回来，这叫粘包。
3. 因此不能认为 recv 一次就是一条完整消息。

二、解决办法

本项目使用“消息头 + 消息体”：

P13/1 TYPE STATUS BODY_LENGTH\r\n
JSON 消息体

接收流程：

1. 先读到换行符，得到完整消息头。
2. 解析协议版本、消息类型、状态码和消息体长度。
3. 按消息体长度循环 recv，直到收满。
4. 再解析 JSON 消息体。

三、本项目对应文件

client/protocol.c
client/protocol.h
server/protocol.py
PROTOCOL.md

四、过关标准

能够说明为什么需要 BODY_LENGTH，并能解释完整发送和完整接收为什么必须循环。


第四阶段：并发连接和节点状态
============================================================

模块四：select 和线程池

一、要学什么

1. select 用来等待网络事件，避免阻塞式死等或循环空转。
2. 监听线程只负责 accept，不应在主循环里处理完整任务。
3. ThreadPoolExecutor 使用固定数量的工作线程处理多个客户端。
4. 多线程共享任务状态时必须加锁。

二、本项目流程

1. select 等待监听套接字。
2. accept 得到客户端连接。
3. 把连接提交给线程池。
4. 工作线程执行认证、心跳、任务分发和结果接收。
5. task_state 使用 RLock 保护共享数据。

三、本项目对应文件

server/server.py
server/task_state.py
server/task_service.py

四、过关标准

能够解释为什么多个节点同时提交结果时需要锁，以及不加锁可能出现什么错误。


模块五：登录、心跳和持续在线

一、要学什么

1. 登录状态表示身份是否认证成功。
2. 心跳用于证明连接仍然存活。
3. 等待任务、计算中、已提交和离线是不同的节点状态。
4. 连接异常时客户端可以重连，但用户主动退出后不应自动重连。

二、持续在线流程

认证成功 → 发送心跳 → 等待任务 → 执行任务 → 提交结果 →
继续等待 → 周期心跳 → 收到下一任务。

三、本项目对应文件

server/task_service.py
client/client_logic.c
client/client_gui.c

四、过关标准

能够根据服务端界面中的状态判断节点处于认证、等待、计算还是离线阶段。

模块七：任务拆分

一、要学什么

假设总区间为 start 到 end，要拆成 N 个子任务。

基本思路：

1. 计算总元素个数。
2. 按比例计算每一轮的起点和终点。
3. 保证所有区间连续、不重叠、不遗漏。
4. 每个子任务生成唯一任务 ID。

示例：1 到 100，拆成 5 份：

第1轮：1 到 20
第2轮：21 到 40
第3轮：41 到 60
第4轮：61 到 80
第5轮：81 到 100

二、本项目对应文件

server/task_planner.py

三、过关标准

能够手算一个区间的拆分结果，并验证边界没有重复和遗漏。


模块八：可扩展运算

一、要学什么

不同运算包括两部分：

1. 客户端如何计算一个子区间。
2. 服务端如何把多个子任务结果合并成最终结果。

现有运算：

区间求和：子任务求和，最终结果继续相加。
区间计数：子任务统计数量，最终结果相加。
区间最小值：子任务求最小值，最终取所有结果的最小值。
区间最大值：子任务求最大值，最终取所有结果的最大值。

二、本项目对应文件

第六阶段：哈希、随机数和 HMAC
============================================================

模块九：SHA-256 哈希

一、要学什么

1. 哈希把任意长度数据变成固定长度摘要。
2. 同样输入得到同样摘要。
3. 输入稍微变化，摘要会明显变化。
4. 哈希不可逆，不等于加密。

二、项目中的用途

1. 计算客户端可执行文件哈希，检查程序是否被修改。
2. 构造 Merkle Tree。
3. 为任务签名准备摘要。

三、本项目对应文件

client/security.c
server/credential_store.py
server/merkle.py


模块十：安全随机数

一、要学什么

普通 rand 不适合安全用途。身份认证和安全会话需要不可预测的随机数。

二、项目中的用途

1. 客户端随机数 client_nonce。
2. 服务端随机数 server_nonce。
3. 会话 ID。
4. 安全消息中的随机量。

三、本项目对应文件

client/security.c

模块十一：HMAC 身份认证

一、要学什么

HMAC 使用双方共享密钥，为消息生成认证标签。它可以证明：

1. 消息来自持有密钥的一方。
2. 消息在传输中没有被修改。

二、登录流程

1. 客户端读取自己的节点密钥。
2. 客户端组合节点 ID、许可证 ID、时间戳、随机数和程序哈希。
3. 客户端计算 HMAC 标签并发送 AUTH。
4. 服务端读取该节点对应密钥，重新计算 HMAC。
5. 两个标签一致，身份认证通过。

三、本项目对应文件

client/credentials.c
client/security.c
server/credential_store.py
server/provision.py

四、过关标准

能够解释为什么攻击者只修改 node_id 不能伪装成其他节点。

第八阶段：加密会话与抗重放
============================================================

模块十四：会话密钥

一、要学什么

1. 长期节点密钥只用于认证和派生会话密钥。
2. client_nonce、server_nonce 和 session_id 共同参与会话密钥派生。
3. 不同连接得到不同会话密钥。

二、认证后流程

AUTH → AUTH_OK → 验证服务端证明 → 派生会话密钥 →
后续消息装入 SECURE 安全信封。

模块十五：消息加密、认证和序号

一、要学什么

安全消息包含：

1. session_id：属于哪个会话。
2. sequence：消息序号。
3. nonce：随机量。
4. ciphertext：加密后的消息。
5. tag：完整性认证标签。

接收方处理顺序：

1. 检查会话 ID。
2. 检查消息方向和序号。
3. 验证认证标签。
4. 验证成功后解密。
5. 解析内部业务消息。

二、抗重放原理

旧消息的 sequence 已经使用过。攻击者再次发送旧消息时，接收方发现序号不是
预期值，因此拒绝处理。

三、过关标准

能够区别“加密解决保密性”和“HMAC 解决完整性与身份认证”。


第九阶段：RSA 数字签名
============================================================

模块十六：任务签名和验签

一、要学什么

1. 服务端持有 RSA 私钥，客户端持有 RSA 公钥。
2. 服务端使用私钥对任务内容签名。
3. 客户端使用公钥验证签名。
4. 公钥可以验证签名，但不能伪造服务端签名。

二、被签名的任务内容

任务 ID | 运算类型 | 起始值 | 终止值

三、客户端处理流程

1. 收到 TASK。
2. 按固定顺序重新组成任务原文。
3. 使用公钥验证 RSA-SHA256 签名。
4. 验签成功才执行计算。
5. 验签失败立即停止，不执行被篡改任务。

四、本项目对应文件

第十阶段：Merkle Tree 结果完整性证明
============================================================

模块十七：Merkle Tree

一、要学什么

1. 客户端把一个子任务再分成 4 个计算步骤。
2. 每一步的计算内容和结果生成叶子哈希。
3. 两两组合哈希，最后得到 Merkle 根。
4. 客户端返回总结果、四步结果和 Merkle 根。
5. 服务端重新计算并验证根哈希及合并结果。

二、简单结构

步骤1哈希 ----\
              中间哈希1 ----\
步骤2哈希 ----/              \
                              Merkle 根
步骤3哈希 ----\              /
              中间哈希2 ----/
步骤4哈希 ----/

三、本项目对应文件

client/merkle.c
client/merkle.h
server/merkle.py

四、必须理解

Merkle Tree 证明的是“返回的总结果与提交的计算步骤一致”。
多个节点冗余计算和多数表决负责判断“哪个结果可信”。两者作用不同。


第十一阶段：冗余计算和多数表决
============================================================

模块十八：同一任务分给多个节点

一、要学什么

为了防止单个恶意节点污染结果，同一个子任务至少分给 3 个不同节点。

示例：

node-01 返回 210
node-02 返回 210
node-03 返回 211

严格多数结果为 210。

二、严格多数规则

需要票数 = 节点数 // 2 + 1

3 个节点至少需要 2 票一致。
5 个节点至少需要 3 票一致。

不是把结果取平均，也不是把“10% 恶意节点”写死进检测逻辑。

三、本项目对应文件

server/task_service.py 中的 choose_majority 和 finish_task。

四、过关标准

能够计算任意节点数量需要多少票，并说明没有严格多数时为什么应该判定失败。


第十二阶段：信誉、积分与恶意节点识别
============================================================

模块十九：信誉更新

一、要学什么

1. 节点结果等于可信结果，增加信誉。
2. 节点结果不等于可信结果，扣除信誉。
3. 持续多轮提交错误结果，错误次数累积。
4. 达到异常轮数阈值后标记为恶意节点。
5. 低信誉或恶意节点不再获得重要任务。

二、本项目对应文件

server/task_service.py
server/scheduler.py
server/task_state.py
server/config.py

三、必须理解

题目中的“不超过 10% 恶意节点”是考核场景，不是把检测比例写死为 10%。
检测依据是节点长期行为、结果一致性、错误轮数和信誉阈值。

4. WindowProc 处理按钮、关闭窗口和自定义消息。
5. 网络任务不能放在 UI 主线程，否则界面会卡死。
6. 后台线程执行 run_client，再把进度通知主窗口。

二、本项目对应文件

client/client_gui.c
client/client_logic.c

三、过关标准

能够说明为什么 client_gui.c 只做显示，而连接、认证和计算放在 client_logic.c。


第十五阶段：异常处理和安全测试
============================================================

模块二十五：异常处理

需要理解的异常场景：

1. 服务端未启动，客户端连接失败。
2. 网络中断，客户端超时并重连。
3. 收到的消息头或 JSON 不合法。
4. 节点 ID、许可证或程序哈希不合法。
5. HMAC 错误。
6. 重放旧消息。
7. 任务签名错误。
8. Merkle 证明错误。
9. 重复提交结果。
10. 节点数不足，无法形成严格多数。

处理原则：

校验输入 → 明确返回错误 → 保存安全事件 → 释放连接和敏感数据 →
不执行未经验证的任务。

5. 登录随机数重放拦截。
6. TCP 粘包和拆包处理。
7. 非法任务输入拦截。
8. 客户端源码危险函数静态检查。

第十六阶段：把全部模块串成一次完整运行
============================================================

最后按下面顺序跟踪一次真实任务：

1. server/gui.py 收集运算参数。
2. process_manager.py 启动 server.py。
3. server.py 监听 TCP 端口并接收客户端。
4. client_gui.c 启动后台线程。
5. client_logic.c 调用 network.c 建立 TCP 连接。
6. credentials.c 读取许可证并计算程序哈希。
7. 客户端发送 AUTH，credential_store.py 完成认证。
8. 双方通过 secure_channel 建立安全会话。
9. 客户端发送 HEARTBEAT，node_registry.py 更新在线状态。
10. task_planner.py 生成当前子任务区间。
11. signature.py 使用私钥签名任务。
12. task_service.py 通过安全会话发送 TASK。
13. 客户端 signature.c 验证任务签名。
14. operations.c 执行对应运算。
15. merkle.c 生成四步计算证明。
16. 客户端发送 RESULT。
17. 服务端 merkle.py 验证证明。
18. task_service.py 收集节点结果并进行多数表决。
19. operations.py 合并可信子任务结果。
20. scheduler.py 更新重要任务节点资格。
21. audit.py 和 security_audit.py 保存记录。
22. evaluation.py 生成考核指标。
23. gui.py 更新结果、信誉、在线状态和日志。
24. 客户端继续在线等待下一任务。

============================================================
