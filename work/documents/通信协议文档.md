# 通信协议文档

分布式计算任务安全分发与结果审计平台

文档编号：P13-CP-001；版本：1.0；日期：2026年11月11日。

## 1 适用范围与报文格式

P13/1 是本项目客户端与服务端之间的 TCP 应用层协议，覆盖身份认证、在线心跳、任务分发、结果提交和退出。默认连接 127.0.0.1:8888。认证前使用 AUTH、AUTH_OK 和 ERROR 帧；认证后统一使用 SECURE 帧，具体业务类型放在解密后的 action 字段中。

```text
P13/1 <message_type> <status> <body_length>

<JSON Body>
```

上式第一行末尾只有一个 LF 字节，即 0x0A；图示中的空行仅用于区分 Header 与 Body，不发送额外空行。Header使用ASCII，Body使用UTF-8。body_length是Body编码后的字节数，不是字符数，也不包含Header。Body不以换行作为边界。

| 字段 | 定义 |

|---|---|

| 版本 | 固定字符串 P13/1 |

| message_type | AUTH、AUTH_OK、SECURE或ERROR；Python端允许字母数字及下划线 |

| status | 客户端请求通常为0；服务端成功为200，失败使用对应状态码 |

| body_length | JSON对象编码后的字节数；至少2字节 |

| JSON规则 | 顶层必须为对象；联调使用紧凑JSON，不在键与冒号之间加入空白 |

### 1.1 边界与兼容约束

Python端配置Header上限为128字节、Body上限为8192字节。C端Header数组为128字节，Body数组为8192字节，并为字符串终止符预留空间；跨端报文应使用保守公共范围：Header含LF不超过127字节，Body不超过8191字节。密文采用十六进制编码后约膨胀两倍，因此业务明文的可用长度明显小于外层Body上限。

Python端按单字节读取到LF，再循环读取指定长度Body。C协议模块按行读取Header并调用network_receive_exact读取Body；当前网络实现缺少该接口定义，且现有network_receive_line可能丢弃同次recv中LF后的数据。客户端粘包拆包能力必须补齐网络实现后再做联调确认。

### 1.2 最小帧示例

```text
P13/1 ERROR 400 16
{"detail":"bad"}
```

此示例Body恰为16个ASCII字节。实现应根据实际UTF-8编码动态计算长度，不能照搬带示意字段报文的固定长度。

## 2 身份认证与密钥建立

### 2.1 AUTH 请求

方向为客户端至服务端，外层类型AUTH，状态0。所有字段使用下表名称；persistent推荐显式发送0或1。节点ID在C端限制为非空且少于64字节，只允许字母数字、短横线和下划线。

| 字段 | 类型与长度 | 含义 |

|---|---|---|

| node_id | 字符串 | 已签发凭据的节点标识，如node-01 |

| license_id | 字符串 | 与节点绑定的许可证ID |

| timestamp | 整数 | Unix秒时间戳；服务端允许±60秒 |

| client_nonce | 32位十六进制字符串 | 16字节安全随机数，登录去重 |

| exe_hash | 64位十六进制字符串 | 客户端可执行文件的SHA-256 |

| auth_tag | 64位十六进制字符串 | 使用节点身份密钥生成的HMAC-SHA256 |

| persistent | 整数0或1 | 0为单次任务，1为持续在线等待；未提供时服务端按false处理 |

认证文本按以下顺序连接，不插入空格，timestamp与persistent使用十进制文本。auth_key为部署分发的32字节节点密钥，仅保存在凭据文件中，不随AUTH传输。

```text
auth_text = node_id|license_id|timestamp|client_nonce|exe_hash|persistent
auth_tag  = HMAC-SHA256(auth_key, UTF8(auth_text)).hex()
```

### 2.2 AUTH_OK 响应

| 字段 | 类型 | 说明 |

|---|---|---|

| session_id | 24位十六进制字符串 | 12字节随机会话标识 |

| server_nonce | 32位十六进制字符串 | 16字节服务端随机数 |

| server_proof | 64位十六进制字符串 | 服务端持有节点密钥的证明 |

| license_status | 字符串 | 成功时为valid |

| integrity_status | 字符串 | 成功时为valid |

```text
proof_text = SERVER|session_id|client_nonce|server_nonce
server_proof = HMAC-SHA256(auth_key, UTF8(proof_text)).hex()
key_text = SESSION|client_nonce|server_nonce|session_id
session_key = HMAC-SHA256(auth_key, UTF8(key_text))
```

客户端先验证server_proof，再使用派生的32字节session_key进入安全会话。任何许可证归属、有效期、时间窗、随机数、程序白名单或身份标签不符合要求的请求均拒绝。当前实现中白名单非空时才执行哈希成员校验，部署验收应确认白名单已经生成。

## 3 安全信封与字节级计算

认证后的外层报文类型固定为SECURE，Body为安全信封。请求外层状态为0，响应外层状态为200或错误状态。业务JSON加密前必须包含action字段。C2S表示客户端发送，S2C表示服务端发送，双方分别维护发送序号与接收序号，初始值为0，首条消息使用1。

| 字段 | 类型与格式 | 作用 |

|---|---|---|

| session_id | 字符串 | 必须与本连接建立的会话一致 |

| sequence | 正整数 | 必须等于该方向上预期的下一个序号 |

| nonce | 32位十六进制字符串 | 每条消息新生成16字节随机数 |

| ciphertext | 十六进制字符串 | 业务JSON的UTF-8字节加密结果 |

| tag | 64位十六进制字符串 | 覆盖方向、会话、序号、nonce和密文的认证标签 |

### 3.1 加密算法

先将业务对象序列化为紧凑JSON并编码为UTF-8。使用下式生成足够长度的密钥流，按长度截断，与明文字节逐位异或。密钥流计数器从0开始；sequence为8字节无符号大端序，counter为4字节无符号大端序，nonce使用原始16字节。方向和会话ID使用ASCII。

```text
prefix = ASCII(direction) || 0x7C || ASCII(session_id) || 0x7C
         || BE64(sequence) || nonce
block[i] = HMAC-SHA256(session_key, prefix || BE32(i))
stream = block[0] || block[1] || ...
ciphertext = plaintext XOR stream[0:len(plaintext)]
```

### 3.2 认证标签与接收

```text
tag_text = direction|session_id|sequence|nonce_hex|ciphertext_hex
tag = HMAC-SHA256(session_key, UTF8(tag_text)).hex()
```

上述tag_text中的sequence为十进制文本，nonce和密文使用小写十六进制。接收端校验会话、严格序号、nonce长度和HMAC标签后，再解密并解析JSON对象。篡改、旧序号和方向不匹配应拒绝。Python SecureSession在验证失败时回退本次预增的接收序号。

### 3.3 安全边界

该信封认证文本未包含外层Header中的message_type、status或body_length；业务action在密文内部。当前方案没有临时密钥交换，不具备已证明的前向保密属性。源码定义的SESSION_TIMEOUT_SECONDS=30尚未形成可观察的强制会话到期检查；不得把它理解为30秒自动换钥。

## 4 业务动作与字段

下表描述SECURE解密后的业务对象。除表中字段外，每个对象均须带action字符串。ACCEPTED表示结果已通过提交层检查并存入，不表示当前值最终赢得多数表决。

| 动作与方向 | 字段 | 处理规则 |

|---|---|---|

| HEARTBEAT；C → S | sent_at：整数 | Unix秒时间戳；服务端当前只检查其大于0 |

| HEARTBEAT_ACK；S → C | server_time：整数 | 服务端Unix秒时间 |

| WAIT；S → C | retry_after：整数；all_complete：布尔 | 当前默认间隔2秒；C端接受1至5秒，否则回退2秒 |

| TASK；S → C | task_id：字符串；operation：字符串；start、end：整数；signature：十六进制字符串 | operation为四类运算标识之一；客户端必须先验签 |

| RESULT；C → S | task_id、node_id：字符串；value：整数；merkle_root：字符串；proof_steps：字符串 | 任务与节点必须对应当前连接；证明一致且未重复提交 |

| ACCEPTED；S → C | task_id：字符串 | 本节点结果已入库到本轮内存结果集合 |

| LOGOUT；C → S | 无额外字段 | 当前持续在线等待分支处理退出；不定义单独退出确认动作 |

| ERROR；S → C | detail：字符串 | 外层status提供错误类别；客户端结束当前会话 |

### 4.1 任务签名

```text
task_text = task_id|operation|start|end
signature = RSA-2048-SHA256-PKCS1-v1_5(task_text).hex()
```

start和end使用有符号十进制文本，operation保持字母大小写。2048位RSA签名为256字节，十六进制表示为512字符。客户端使用client/task_public.key中的公钥验证；签名不匹配时停止执行。

### 4.2 结果证明

proof_steps不是数组，而是四个十进制整数以逗号连接的字符串，例如1275,3775,6275,8775。对每个值的十进制文本做SHA-256得到64字符小写十六进制叶子；相邻叶子文本拼接后再做SHA-256，最后拼接两个中间哈希文本并哈希得到根。拼接的是哈希文本，不是32字节原始摘要。

示例：SUM_RANGE计算1至200，四步值为1275、3775、6275、8775，value为20100，merkle_root为11a35f8bb4b015ed2eea741b278b0f3fcaadbb17b2518033598ec9f3acd785f4。其他运算按对应合并规则得到value。

## 5 会话顺序与错误处理

```text
客户端                         服务端
AUTH ------------------------> 许可证与身份认证
     <---------------- AUTH_OK 会话参数与服务端证明
SECURE / HEARTBEAT -----------> 验证序号和心跳
     <--------- HEARTBEAT_ACK
     <------------------ TASK  签名任务
验签并四段计算
SECURE / RESULT -------------> 身份、任务、证明、重复检查
     <-------------- ACCEPTED
     <------------------ WAIT 持续在线模式无新任务
HEARTBEAT / ACK 循环，后续出现新TASK时继续执行
SECURE / LOGOUT -------------> 等待分支退出并关闭连接
```

持续在线客户端在完成一个任务后仍可等待下轮任务。非持续模式若当前轮次无法领取任务，服务端返回409并关闭连接。节点在已分配但未成功提交时断开，服务端释放该节点的领取名额。

| 状态码 | 含义 | 典型触发条件 |

|---|---|---|

| 200 | 成功 | 认证、心跳和提交处理成功 |

| 400 | 格式或顺序错误 | Header、JSON、消息类型或action不符合要求 |

| 401 | 认证失败 | 凭据失败、安全信封校验失败 |

| 403 | 身份不匹配 | RESULT中的节点或任务与分配不符 |

| 409 | 状态冲突 | 重复提交、任务过期、当前轮次无可领取任务 |

| 413 | 消息超限 | 长度非法或Body过大 |

| 422 | 结果不可处理 | 结果字段无效、Merkle证明不匹配；当前超时处理亦可能使用该码 |

| 500 | 服务端错误 | 未预期的内部异常 |

认证前错误使用明文ERROR帧，Body为含detail的JSON对象；认证后尽量使用SECURE包裹ERROR动作。底层网络断开不保证能发送错误报文。服务端处理套接字超时为8秒，C网络文件对收发设置5秒超时，connect本身未实现独立超时控制。

### 5.1 联调验收要点

应验证跨端紧凑JSON、UTF-8字节长度、双向独立序号、连续帧与逐段发送、错误状态码、非空程序白名单、篡改和重放拒绝，以及持续在线时的WAIT循环。客户端缺失网络接口补齐前，当前Python端测试结果不能作为C端收包能力的验收依据。
